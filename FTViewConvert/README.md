# FTView Convert

Перекодирует любое видео в MJPEG AVI для двух выводов: **VDAC2** (плагин FTView,
FT812, звук на General Sound или FT812) и **VDAC4** (плагин FTVIEW4, ядро видео
Tang Nano 20K). Windows x64, одно окно с английским интерфейсом: выбор файла,
папка результата («Open folder» показывает её в проводнике), обрезка боковых
сторон до 4:3, режим («Mode»: VDAC2 или VDAC4), нормализация звука и «Convert».
По окончании появляется сообщение «Video converted». Файл можно перетащить в
окно или на значок программы.

## FFmpeg

Всё перекодирование видео и звука делает [FFmpeg](https://ffmpeg.org/) —
свободный проект, который много лет создают и поддерживают разработчики
FFmpeg. Спасибо им за эту работу. FTViewConvert подбирает параметры, запускает
FFmpeg и дописывает в готовый файл таблицу перемотки для плеера.

- Встроенная сборка — FFmpeg 9.0.2 «essentials» с
  [gyan.dev](https://www.gyan.dev/ffmpeg/builds/): на неё ссылается страница
  загрузки ffmpeg.org.
- Лицензия — GNU GPL v3, её текст — `ffmpeg-LICENSE.txt` рядом с программой.
- Исходный код FFmpeg: <https://ffmpeg.org/download.html>.

## Режимы

| | VDAC2 | VDAC4 |
|---|---|---|
| Кадр | до 512×384 по площади: 16:9 — 512×288, 4:3 — 512×384 | в пределах 640×480: 16:9 — 640×360, 4:3 — 640×480 |
| Видео | MJPEG ~2 Мбит/с, своя матрица, стандартные таблицы Хаффмана | MJPEG ~2,8 Мбит/с, матрица MPEG-1, свои таблицы Хаффмана в каждом кадре |
| Звук | PCM 8 бит моно 32 000 Гц | MP3 44,1 кГц 16 бит стерео, ~192 кбит/с |
| Нормализация | пик до 0 дБ, тихие записи — ещё до +2 дБ | пик до −1 дБ |
| Таблица перемотки FTView | встраивается | нет |

Видео в обоих режимах — MJPEG baseline 4:2:0, **24 кадра/с**. Каждый видеочанк —
целый JPEG: разрыв меток времени исходника (видео позже звука, плавающий
темп) заполняется копией кадра (`-fps_mode cfr`). По умолчанию ffmpeg для AVI
пропускает такой разрыв, и мультиплексор отмечает его пустыми чанками `00dc`:
у ролика, где видео начинается на 0,5 с позже звука, их было 13. Нормализация
и «Crop 4:3» работают в обоих режимах.

## VDAC2

- Видео: стандартные таблицы Хаффмана, около 2 Мбит/с — как у проверенного
  образца Muse (≈250 КБ/с чтения с SD).
- **Меньше квадратиков.** Своя матрица квантования: стандартная MPEG-1 (её
  ffmpeg берёт по умолчанию), но низкие частоты квантуются мельче (×0,6 и
  ×0,9), высокие крупнее (×1,6 и ×2,4). При том же потоке внутри блоков 8×8
  остаются плавные переходы. Квадратики на градиентах и в цвете (блок цвета
  при 4:2:0 — 16×16 точек, на экране почти 30×30) заметно слабее: по
  `blockdetect` у Muse 7,8 вместо 9,3 по яркости и 10,2 вместо 13,1 по цвету,
  у КИНО цвет 10,2 вместо 15,7. SSIM к исходнику почти прежний. Таблица
  по-прежнему одна на яркость и цвет. Trellis-квантование и шумоподавление
  перед сжатием (`hqdn3d`) квадратики не уменьшали, trellis их даже усиливал.
  Совсем убрать квадратики нельзя: 2 Мбит/с на 512×384 — около 0,4 бита на
  точку, а поток ограничен чтением с SD.
- Звук (если он был в исходнике) — PCM 8 бит без знака (araw) моно
  32 000 Гц. Его выводит ЦАП General Sound (до 37,5 кГц — частота прерываний
  GS), а без GS — звуковой блок FT812 (плагин переводит байты в знаковые).
  Звук занимает 32 КБ/с потока, передача в GS — около 17% времени Z80. Моно —
  потому что звуковой блок FT812 одноканальный.
- Индекс `idx1` и **готовая таблица перемотки** плеера: чанк `JUNK` перед
  `idx1` (другие плееры его пропускают). Первая перемотка в плеере не
  разбирает `idx1`, а загружает таблицу одним чтением: для Muse в Unreal
  1,1 с вместо 6,7 с. Таблица считается так же, как её строит сам плеер
  (эталон — `tests/avigen.py`, `seek_table`), и сверяется с полями
  заголовка файла.

## VDAC4

Кадр MJPEG в VDAC4 декодирует ПЛИС — ядро видео Tang Nano 20K, файл ему подаёт
плагин FTVIEW4; звук MP3 декодирует ESP (VIDEO.ELF). С ядра 1.43 у декодера
свой деблокер: окно края блока 8×8 (по 4 точки с каждой стороны) сглаживается,
если размах зелёной в нём меньше 2·QP, а QP — половина большего из шагов DC и
первого AC таблицы квантования яркости из файла. Под это подобраны параметры:

- **Матрица квантования — стандартная MPEG-1** (ffmpeg берёт её по
  умолчанию), а не матрица VDAC2: у той первый AC мельче, и деблокер
  сглаживал бы меньше. Таблица одна на яркость и цвет: вторую таблицу ядро не
  держит — она затирает первую.
- **Таблицы Хаффмана — свои для каждого кадра** (`-huffman optimal`): ядро
  берёт DHT из кадра, а файл при том же качестве на 9–14% меньше (куры — 8,5%,
  Muse — 13,7%).
- **Поток — 2,8 Мбит/с**: кадр в 1,56 раза больше, чем в VDAC2 (640×360
  против 512×288, 640×480 против 512×384). Файл со звуком читается в среднем
  ~370 КиБ/с, в пике до ~540 КиБ/с за секунду — как «Кино» (371 и 564 КиБ/с),
  которое ядро на плате проигрывало ровно.

Параметры выбраны на модели показа: декодер с размножением цветности, как в
ядре, и деблокер по эталону стенда ядра (`tb_vp.cpp`). Против параметров
VDAC2 на том же кадре:

| Ролик | Кадр | PSNR яркости, дБ | Ступенька на краях блоков |
|-------|------|------------------|---------------------------|
| Muse | 640×480 | 39,6 → 44,3 | 0,89 → 0,65 |
| «Кино» | 512×384 | 45,1 → 52,9 | 1,16 → 0,86 |
| Куры, 854×480 | 640×360 | 30,6 → 32,5 | 2,97 → 2,51 |

Ступенька — средний перепад яркости поперёк края блока сверх перепада внутри
блоков, уже после деблокера. У кур 2 Мбит/с недостижимы вовсе: при
параметрах VDAC2 кодер упирается в предельный шаг квантования и выдаёт
2,56 Мбит/с. Фильтры перед сжатием (`hqdn3d`, `gblur`) квадраты почти не
убирали, а картинку мылили (`gblur` у «Кино» — −3,6 дБ PSNR). Наклон матрицы
в духе VDAC2 (мельче низкие частоты, крупнее высокие) с деблокером ядра
стандартную матрицу ни по ступенькам, ни по PSNR не обгонял.

Звук — MP3 44 100 Гц, 16 бит, стерео, переменный поток около 192 кбит/с —
LAME V2 (`libmp3lame -q:a 2`), на записи с плотным звуком 180–200 кбит/с
(Muse — 186). Поток в AVI — `0x0055` MP3. **FTView (VDAC2) такой звук не
играет**: ни General Sound, ни FT812 MP3 не декодируют. Таблица перемотки
FTView в файл VDAC4 не встраивается: она считает звуковые байты сэмплами PCM.

- `nAvgBytesPerSec` в заголовке звука — настоящий средний поток файла: байты
  чанков звука по `idx1` на длительность звука из `strh`. Мультиплексор AVI
  ffmpeg пишет туда битрейт кодека, а у LAME с переменным потоком его нет —
  выходил 0. VIDEO.ELF по этому полю переводит байты MP3 во время: сколько
  звука можно выбросить, когда он отстал, и сколько выброшено при
  переполнении кольца; при 0 и то и другое — ноль.
- Звук начинается с 25 мс тишины — задержки кодера LAME (1105 сэмплов). Видео
  на неё не сдвигается: при 24 кадрах/с сдвиг округлялся до кадра, и за первым
  кадром мультиплексор вставлял пустой видеочанк.

## Нормализация звука

Галочка «Normalize audio level (VDAC2 to 0 dB, VDAC4 to -1 dB)», по умолчанию
включена. Первый проход («Measuring audio level…») замеряет пик (`astats`) и
громкость (EBU R128) того самого звука, что пойдёт в файл: уже на частоте и с
числом каналов результата, в плавающей точке (сведение стерео в моно даёт
пики до +3 дБ, понижение частоты — выбросы выше пиков исходника). Второй
усиливает весь звук одним множителем.

- **VDAC2:** самый громкий сэмпл выходит на полную шкалу 8 бит. Запись,
  которая и после этого тише −12 LUFS, поднимается ещё не больше чем на
  2 дБ: вылезшие за шкалу пики мягко прижимает лимитер `alimiter` с длинной
  атакой — 50 мс, восстановление 1 с. Сжатие не глубже 2 дБ, громкие записи
  только нормализуются. Прежние атака 5 мс и восстановление 50 мс меняли
  усиление за пару периодов баса, и сжатие было слышно. Замеры: Muse
  +1,9 дБ, лимитер прижимает пики до 1,6 дБ; «Кино» +0,1 дБ — только
  нормализация; Muse, ослабленный на 20 дБ, +21,9 дБ — результат совпадает с
  обычным Muse с точностью до округления в 8 бит. LRA почти не меняется
  (Muse 3,2 → 3,0 LU). У 8 бит
  всего 48 дБ, и тихий звук без нормализации тонет в шуме квантования.
- **VDAC4:** пик поднимается только до −1 дБ: декодер MP3 восстанавливает
  волну с выбросами выше исходных пиков (у Muse после декодера пик −0,9 дБ),
  при 0 дБ они срезались бы. Подъёма тихой записи лимитером нет — 16 бит
  тихий звук не теряют. Замеры: Muse +1,1 дБ, «Кино» +0,6 дБ.

## Файл результата

По умолчанию кладётся рядом с исходником: `<имя> - FTView 512x288 24p 32 kHz.avi`
(VDAC2) или `<имя> - VDAC4 640x360 24p MP3.avi` (VDAC4). Папку и имя можно
сменить кнопкой «Change…» в строке «Save to»; выбранная папка остаётся и для
следующих файлов.

## Если Windows не даёт записать файл

Программа сама пробует записать в папку результата сразу после выбора
исходника и перед запуском, и называет причину под кнопкой «Convert»:

- файл с таким именем открыт в другой программе (плеер) или помечен «только
  для чтения» — закройте её или выберите другое имя;
- писать в папку можно только с правами администратора (проводник в этом
  случае спрашивает разрешение, а обычным программам Windows отказывает) —
  выберите другую папку или запустите программу от имени администратора;
- папку охраняет «Контролируемый доступ к папкам» Защитника Windows —
  разрешите в нём `FTViewConvert.exe` и
  `%LOCALAPPDATA%\FTViewConvert\ffmpeg-9.0.2.exe` или выберите другую папку.

Если проверка не прошла, «Convert» предлагает выбрать другое место.

## Как считается разрешение

Кадр — с пропорциями исходника (с учётом SAR/DAR и поворота видео с телефона)
и не больше самого исходника: маленькое видео не растягивается.

**VDAC2:** стороны кратны 16 (блок JPEG 4:2:0: неполный блок на краю декодер
FT812 дописал бы в соседний кадр), площадь не больше 512×384 = 196 608 точек.
Это предел плеера, при котором работают и звук через FT812, и таблица
перемотки в RAM_G. Ширина до 1024, высота до 768.

Пропорции важнее площади. Среди кадров не меньше 60% наибольшего возможного
берётся наибольший с ошибкой пропорций не больше 0,5%, а если такого нет —
самый точный. Прежнее правило «наибольшая площадь» давало для 16:9 кадр
576×320 (9:5, шире на 1,25%). Точный 512×288 при потоке 2 Мбит/с на экране не
хуже: на клипе 16:9 (растяжение до 1024×576 со сглаживанием) SSIM 0,6365
против 0,6350, а квадратиков на 29% меньше — на точку приходится больше бит.

**VDAC4:** кадр вписывается в 640×480, стороны чётные. Ядро кладёт кадр с
9·ширина ≥ 14·высота на холст 16:9 — наименьший из 512×288, 640×360 и
1024×576, куда он входит. Такой кадр выше 360 строк ушёл бы на холст 1024×576
и на экране был бы мельче, поэтому он вписывается в 640×360 (16:10 —
576×360, а не 640×400).

| Исходник | VDAC2 | VDAC4 |
|----------|-------|-------|
| 16:9 (1920×1080, 4K, DVD и HDV 16:9) | 512×288 | 640×360 |
| 4:3 | 512×384 | 640×480 |
| 16:10 | 512×320 | 576×360 |
| 3:2 | 528×352 | 640×426 |
| 1,85:1 | 592×320 | 640×346 |
| 2,39:1 | 608×256 (ошибка 0,5%) | 640×268 |
| 9:16, телефон с поворотом | 288×512 | 270×480 |
| 320×240 | 320×240 | 320×240 |
| 16:9 с «Crop 4:3» | 512×384 | 640×480 |

**Crop 4:3** (галочка «Picture: Crop 4:3», по умолчанию выключена) симметрично
обрезает боковые стороны кадра шире 4:3, высота остаётся. Картинка занимает
весь экран без полос сверху и снизу, а разрешение считается уже по
обрезанному кадру: у 16:9 — 512×384 (VDAC2) или 640×480 (VDAC4). Учитываются
SAR (DVD 16:9 720×576) и поворот видео с телефона: режется то, что на экране
по бокам. Кадр 4:3 и уже (вертикальное видео) не меняется, верх и низ не
обрезаются — в строке «Result» тогда написано «not wider than 4:3: not
cropped».

## Готовая сборка

Архив `FTViewConvert.zip` (~37 МБ) лежит в релизах проекта:
<https://github.com/andrewinsidelazarev/Wild-Commander-Improved/releases>.
Внутри — `FTViewConvert.exe`, лицензия ffmpeg, это описание и исходники
программы (папка `source`, из них exe собирается `build.ps1`). В самом
репозитории сборки нет: иначе её скачивал бы каждый, кто берёт исходники.

## Сборка

```powershell
powershell -ExecutionPolicy Bypass -File build.ps1
```

Нужен только Windows с .NET Framework 4 (компилятор `csc.exe` есть в системе).
Скрипт один раз скачивает статический ffmpeg 9.0.2 (essentials, gyan.dev — на
него ссылается ffmpeg.org), сверяет SHA-256 архива и вшивает `ffmpeg.exe` в
программу ресурсом. Результат — `FTViewConvert/build/FTViewConvert.exe`
(~105 МБ) и `FTViewConvert.zip` для релиза (~37 МБ). При первом запуске ffmpeg распаковывается в
`%LOCALAPPDATA%\FTViewConvert`. Иконка `app.ico` строится скриптом
`make_icon.py` (Python с Pillow) и хранится готовой.

Пакетный режим без окна для сценариев и проверок:
`FTViewConvert.exe --batch <вход> <журнал> [vdac4] [nonorm] [crop43]` (код
выхода 0 — успех, 2 — файл результата записать нельзя; по умолчанию режим
VDAC2 с нормализацией, `vdac4` — режим VDAC4, `nonorm` отключает
нормализацию, `crop43` — обрезка боковых сторон до 4:3),
`--probe <вход> <журнал> [vdac4] [crop43]` — только расчёт разрешения. В
журнале строка `write=` — `ok` или причина, по которой запись невозможна,
`gain=` — усиление второго прохода в дБ (`off` — без нормализации), `index=` —
число записей встроенной таблицы перемотки (0 — не встроена; в режиме VDAC4
всегда 0), `mp3rate=` — `nAvgBytesPerSec`, записанный в заголовок звука
(режим VDAC4; 0 — не записан).

ffmpeg распространяется по GPL v3; его лицензия — `ffmpeg-LICENSE.txt` рядом
со сборкой.
